## 1. 游戏定位与核心体验

**[确认]** 《万界文明》是一款围绕**文明发展、卡牌构筑、世界改造与涌现组合**的幻想战略游戏。用户强调，地图形状不是最终差异化核心，**推动文明与世界变化的机制**才是核心。

**[确认]** 卡牌不是简单的即时技能按钮：它们能改变单位、建筑、地形、网络、文明规则，乃至影响未来的卡牌获得机会。玩家要能够构建意料之外的组合、强大实体、超级文明建筑与奇观。

**[方向]** 呈现形式是一个**大型、真实立体、可交互且可改变的精致实体棋盘世界**，美术目标为高品质幻想桌游微雕，而不是单纯的平面六边形策略 UI。

**[待定]** 具体胜利条件、单局时间、回合/即时制、多人模式、资源经济、抽卡公式与数值平衡；这些不能从已有视觉原型倒推。

## 2. 卡牌系统——已经认可的核心骨架

**[确认] 三层作用对象：**

1. **领主／玩家自身构筑**：领主作为特殊构筑对象；卡组、卡牌机会、解锁、融合及构筑路径可受领主侧能力影响。
2. **文明规则构筑**：改变生产、战争、生态及其他文明层级规则，进而影响全体行为的可能性。
3. **实体与世界构筑**：改变单位、军队、建筑、地貌、城市和相互联结的网络；世界是可持续变化的，不只是一次性的视觉升级。

**[确认] 卡牌作用类型与组合原则：**

- 行动类、部署/实体类、挂靠/附着类、持续生效的文明规则类，以及改变机制本身的特殊卡牌；类别边界允许日后细化。
- 卡牌可以挂靠在**单位、建筑、地形、空间/关系网络**等对象上，并与已存在的卡牌形成组合、修正与连锁效果。
- **过去已选择的卡牌应影响未来卡牌的出现概率、解锁条件或来源**，让构筑发展具有路径依赖，而不是每张卡孤立随机抽出。
- 支持**扩容、复制、融合、层层叠加**，允许出现超大单位、超级城市、异常强大的构筑结果；设计时要保留惊喜和可理解的因果。
- **奇观**可以由实体与网络持续发展和组合形成，不应只剩一个固定按钮“建造奇观”。

**[待定]** 具体卡池、抽取时机与成本、稀有度、卡牌限制、组合公式、冲突处理、规则裁决优先级、回合结算顺序、NPC/AI 构筑算法、平衡约束。

**重要边界：** 不能把以上骨架直接当作某套已经写好的运行时数据结构或已通过测试的程序实现。

## 3. 文明与世界

**[方向]** 允许显著不对称的幻想文明。既往讨论涉及：兽人、精灵、冥界/亡灵倾向文明、地精、矮人、机械、虫族等。它们是**候选的文明/美术与机制方向**，不是已正式冻结的完整可玩阵营列表。

**[确认]** 地图必须是**有空间位置与物理表现的世界**，不能把世界缩减成一层跳转菜单或只供填色的无意义格子；卡牌能让地形、建筑、单位及网络产生可观察的物质改变。

**[方向]** 表层地图与可建筑地块之间应具有区分：道路、河流、山脉、森林等可以跨多个地块连成连续地貌。

## 4. 六边形地块、建筑与空间

**[确认]** 当前主线采用**六边形实体棋盘方向**；其确切六向共边与网格连接是硬技术要求，不能重现早期块状松散拼接与大片露底。

**[确认]** **普通建筑默认一格一座**：一格有一个主建筑的逻辑占位；屋檐、旗帜、雕花等视觉装饰可合理伸出，不自动占用第二格。占格与模型包围盒必须分别建模。对于奇观/特殊构筑的多格例外，需显式定义，不得偷偷破坏普通建筑的规则。

**[确认]** 每格六条边具备可定义的连接接口；**相邻两格必须对同一公共边共享连接事实**，不能各自拥有不一致的「已连接」状态。道路、山脊、河道等连接型地貌应能根据接口旋转、选择模块、组合延伸。

**[方向]** 通过**六向旋转复用模块**，结合标准边中心、连接宽度/高度/断面，降低高精度资产需求；连接精度由引擎或 Blender 标准模板控制，不能指望 AI 自动保证共边。初期不需要复杂全局 WFC；优先确定性的邻接匹配、编辑和校验。

**[方向]** 棋盘基底可以有细微高度差；真正高耸的山体、森林、岩石、河流、建筑等作为独立表层实体或连接模块表现。视觉上应连贯，但数据上分层。

**[待定]** 六边形边长对应的游戏世界尺度、道路接口的最终宽度、建筑对地表的高度适配、地形高差与连通例外规则。早期例子中的 1m 半径、0.5m 道路宽度只是草案值，**非批准的最终制式**。

## 5. 视角与交互

**[方向，已有视觉实验]** 普通战略操作优先**固定倾角、平移、缩放、六向 60° 旋转**，减少任意自由飞行对方向感和画面可读性的破坏；另设**微雕鉴赏模式**供自由旋转/近看高模。

**[方向]** 对比正交、弱透视、中等透视后，现阶段**弱透视**比较契合空间感与策略可读性的折中。但具体视场角、俯仰角与默认相机距离仍需实测调整；不要把演示中的 20°、45° 直接视为永久定稿。

**[确认]** 视觉真实感应来自透视、阴影、遮挡、建筑/地块尺度、自然与人工地貌的空间层次共同组织，而不是一味增加单一光效。

## 6. 目前不能声称已经完成的内容

- GitHub `main` 仍主要是早期 Wanjie Engine 0.4 原型：仓库 README 介绍的数据层/渲染代码**不等于**后续 0.6～1.5 的独立实验已集成。
- 卡牌系统、文明机制、世界涌现与完整游戏循环尚不能因为设计宪章存在就声称已实现。
- 多级 LOD、自动资产烘焙、复杂拼接微雕，以及稳定的大地图性能仍需要真实基准验证。

## 7. 开发与版本协作

**[确认]** 本项目当前以单人主导为主：GitHub 是**长期记忆、代码存档与里程碑交接**，不是每一步 UI/美术试错的强制工作流程。

- 日常视觉/交互迭代先采用**独立可点开的 HTML 原型**与本地数据验证；用户认可后再择机整合主工程。
- **不制造大量 PR 与分支**；适合单人、低冲突的文档和批准里程碑可直接提交 `main`。
- 不能把「代码语法检查通过」写成「真实浏览器渲染/性能已验收」，不能把独立原型写成已在主仓库生效。
- 每次正式定稿更新本文件对应章节，并在下面写清决策日期、用户确认依据、待办影响。

## 10. 卡牌机制骨架与研发流程（2026-10-19）

**[确认]** 新的研发原则为**先机制骨架 → 少量实验内容 → 可玩/可复现实测 → 大量删减与合并 → 再扩充**。单张牌规则尽可能简单；卡牌数字粒度、世界实体/关系、出牌目标、宏观计划与双层新手教学等阶段性结论及候选，完整记于 [CARD_SYSTEM_MECHANICS_RESEARCH_2026-10-19.md](./CARD_SYSTEM_MECHANICS_RESEARCH_2026-10-19.md)。

**严禁混淆：** 扑克牌数字用于研究**操作粒度**，不等于已经决定引入同花顺或固定花色；12张实验牌与4张M0夹具**都不是正式开局卡池**；领主天赋与可操作领主卡牌不是同一概念；宏观卡牌提交战略意图但仍由真实世界组织执行；玩家/开发者必须有可理解且共享事实来源的教程。具体数字语义、抽牌规则、时间与组织公式依然待测。
